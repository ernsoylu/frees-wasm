# D1 — Property backend strategy

**Status:** Decided · **Date:** 2026-07-30 · Supersedes nothing · Informs D2

## Decision

**Precomputed phase-split `(P,h)` property tables, generated offline by native
CoolProp, are the browser build's property backend** — `PLAN.md` §4 option C.
Ship them at

| | |
|---|---|
| saturation-line samples | `n_sat = 512` (uniform in `ln P`) |
| 2-D pieces | `n_p = 144` × `n_dh = 72`, one per phase, three properties each |
| liquid coordinate | **normalized** depth `(h_f − h)/(h_f − h_cold)`, not the reference's absolute `h_f − h` |
| storage | **`f32`** |
| size | **269,152 bytes per fluid** (236 KB gzipped) |

Generated by `tools/table-gen` (format and geometry: its `README.md`), written
to `fixtures/proptables/`. Option A (`coolprop.wasm` behind a JS boundary)
remains the escape hatch, but this measurement moves it from "the fallback for
the common case" to "the fallback for supercritical, humid air, mixtures and
transport properties" — see *What the tables do not cover*.

## Context

`PLAN.md` §4 put three options on the table and asked for measured numbers. The
reason the answer was never obvious is that CoolProp sits in the Newton inner
loop, so its cost multiplies by (variables × iterations × blocks).

Two facts reframed the question before any measurement:

1. **The reference already contains option C, dormant.**
   `props/PhPropertyTable.java` (bicubic Hermite `(P,h)` surface with *analytic*
   partials), `props/SaturationSplitTable.java` (saturation lines + exact
   two-phase relations + two dome-following single-phase pieces) and
   `props/PhTableRegistry.java` (lazy per-fluid registry, 1e-4 validation gate,
   fall-through to the native call) are all shipped and wired into
   `PropertyFunctions.evaluate`. So option C is not a new design to be invented
   and validated — it is an existing, tested design whose *data* has to move
   from runtime native calls to a build-time artifact. `props/phtable.rs` and
   `props/satsplit.rs` exist as port targets for exactly these two classes.

2. **`PhTableRegistry` only ever intercepts `(P, Hmass)` inputs.** Everything
   else — `(P,T)`, `(P,s)`, `(P,x)`, `(T,x)` — reaches CoolProp directly at full
   accuracy. This matters enormously here, because the *pending fluid fixtures
   do not make a single `(P,h)` call*: `rankine-cycle` asks for
   `Enthalpy(Water, P=…, x=0)`, `Enthalpy(Water, P=…, T=480 [C])` and
   `Enthalpy(Water, P=…, s=s3)`. A port that reproduces the reference's table
   path exactly would still have nothing to answer those with. **The port needs
   the inverse lookups the reference never exercises**, so they had to be
   measured, not assumed.

## Verified, not assumed

Everything below is from `tools/table-gen` against **CoolProp 8.0.0**
(`get_global_param_string("version")`, the 12.4 MB `libCoolProp.so` vendored in
`../frEES/backend/core/native/`). Raw output: `fixtures/proptables/MANIFEST.json`
and `ERROR-REPORT.json`; the resolution ladder is reproducible with
`tools/table-gen/run.sh <dir> --sweep`.

### The generator is not a lookalike

`TableGen` builds its grids with the **real** `PhPropertyTable`, and its
restatement of the split geometry (necessary only because
`SaturationSplitTable` hard-codes 256/96/48) is compared against the **real**
`SaturationSplitTable` at that resolution:

```
cross-check vs reference SaturationSplitTable: 1176 points, worst rel diff 0.000e+00   (Water)
cross-check vs reference SaturationSplitTable:  576 points, worst rel diff 0.000e+00   (R134a)
```

Bit-identical. The error numbers below are therefore the error of the code the
Rust port transcribes, not of a stand-in written for the measurement.

### What the native call costs today

20,000 distinct `PropsSI("T", "P", …, "Hmass", …, "Water")` flashes through the
engine's own `CoolProp` façade: **14.68 s, or 734 µs per call.** That is the
JNA + high-level-string-interface path on this machine with the LRU defeated by
distinct keys — it is *not* a measurement of CoolProp's Helmholtz solve in
isolation, and it is *not* a browser number. It is, however, the cost the
reference engine actually pays per Jacobian entry, and it is three to four
orders of magnitude above an array interpolation. Nothing in this decision
turns on the exact figure.

> **Not measured, and it should be:** no end-to-end benchmark of a Rust table
> lookup versus a `coolprop.wasm` call across the JS boundary, and no solve-time
> comparison on a whole document. `PLAN.md` §4 asked for the latter. This
> deliverable measured *accuracy and size*, which is what the grid choice turns
> on; the *speed* half of the spike is still open.

### Accuracy — 4,000 samples per fluid, fixed seed

Sampling matches `PhTableRegistry`'s own validation gate so the numbers are
comparable to its 1e-4 threshold: `P` log-uniform over `[p_min, p_serve_max]`,
`h` uniform over `[h_f(P) − 150 kJ/kg, h_g(P) + 500 kJ/kg]`. Relative error is
`|tab − direct| / max(|direct|, 1e-12)`.

| Query form | Water max | Water rms | R134a max | R134a rms |
|---|---|---|---|---|
| `(P,h) → T` | 1.08e-05 | 3.23e-07 | 9.30e-06 | 3.43e-07 |
| `(P,h) → Dmass` | 4.54e-05 | 1.89e-06 | 5.89e-05 | 1.99e-06 |
| `(P,h) → Smass` | 2.08e-04 | 3.32e-06 | 6.99e-06 | 3.20e-07 |
| `(P,T) → h` *(inverse)* | 2.02e-04 | 6.67e-06 | 9.44e-06 | 4.94e-07 |
| `(P,s) → h` *(inverse)* | 2.14e-04 | 7.12e-06 | 8.56e-06 | 6.28e-07 |
| `(P,x) → h` *(sat line)* | 4.01e-07 | — | 2.28e-07 | — |
| `(T,x) → P` *(sat line)* | 2.77e-06 | — | 2.51e-06 | — |

By region (max over all three properties):

| | liquid | two-phase | vapor |
|---|---|---|---|
| Water | 2.08e-04 (n=224) | 3.88e-05 (n=3061) | 4.54e-05 (n=707) |
| R134a | 2.72e-06 (n=371) | 2.42e-05 (n=1007) | 5.89e-05 (n=584) |

**The single worst number in the whole set is located, not left as a mystery.**
Water's 2.08e-04 is `Smass` in subcooled liquid at `P = 2267 Pa` — essentially
`p_min`, the bottom-left corner of the domain — at `T = 288.6 K` where
`s = 230.5 J/kg·K`. The **absolute** error there is `4.79e-02 J/kg·K`. Water's
entropy reference is zero at the triple point, so relative error is inflated
wherever `s` passes near zero; read that row as "0.05 J/kg·K", not as
"2 parts in 10⁴ of anything meaningful". The two inverse forms inherit the same
corner through the same mechanism.

### The states the pending fixtures actually land on

Aggregate worst-case over a deliberately wide band is the pessimistic number.
These are the thirteen concrete `(P,h)` states the eight pending fluid documents
reach, lifted from `fixtures/corpus-pending/golden/`:

| State | max rel error over T, ρ, s |
|---|---|
| `rankine-cycle` h1 — sat liquid @10 kPa | 6.59e-05 |
| `rankine-cycle` h2 — pump exit @8 MPa | 4.21e-06 |
| `rankine-cycle` h3 — 480 °C steam @8 MPa | 3.79e-07 |
| `rankine-cycle` h4 — wet steam @10 kPa | 2.71e-08 |
| `state-tables` hw_1 — 45 °C liquid @10 kPa | 3.00e-06 |
| `refrigeration-vcr` h1 / h2s / h2 / h3 / h4 | ≤ 2.65e-06 |
| `state-tables` href_1 / href_2 | ≤ 8.78e-07 |
| `ev-battery` hliq — sat liquid @1.2 MPa | 1.13e-07 |

Worst of the thirteen: **6.6e-05**, and that is saturated-liquid *density* at
10 kPa (the `v_f` line at `f32`); every other state is at or below 4e-06.

### Grid choice, justified by the ladder

`--sweep`, `f64`, `n_sat = 256`, normalized liquid, 1500 samples:

| `n_p` × `n_dh` | KB (f64) | Water T / ρ / s | R134a T / ρ / s |
|---|---|---|---|
| 48 × 24 | 73 | 2.28e-4 / 7.19e-3 / 3.47e-4 | 3.39e-4 / 2.40e-3 / 2.51e-4 |
| **96 × 48** *(reference)* | 236 | 2.01e-5 / 6.44e-4 / 3.68e-5 | 1.48e-5 / 7.81e-5 / 1.53e-5 |
| **144 × 72** *(chosen)* | 508 | 9.27e-6 / **8.13e-5** / 1.26e-5 | 8.65e-6 / 7.81e-5 / 6.83e-6 |
| 192 × 96 | 887 | 4.44e-6 / 8.13e-5 / 5.90e-6 | 5.60e-6 / 7.81e-5 / 4.26e-6 |

Reading the ladder:

* **48 × 24 is disqualified** — 7.2e-3 on water density is two orders past the
  reference's own 1e-4 gate.
* **The reference's own 96 × 48 exceeds its own 1e-4 threshold** on water
  density: 6.4e-4. `PhTableRegistry` gates each fluid on 300 fixed-seed samples
  at 1e-4 — and **both fluids pass it**: calling
  `PhTableRegistry.lookup("T","P",1e5,"Hmass",2.7e6,"Water")` on the reference
  jar returns a value, so water and R134a are served from tables in production
  today. That gate is a spot-check, not a bound; a 1500-sample draw finds cells
  six times past it. In the reference that is cheap — the table feeds a Jacobian
  and the answer the user sees still comes from a native call for every
  non-`(P,h)` input. **Here the table *is* the answer**, which is a different
  bar, and a direct argument against inheriting 96 × 48.
* **144 × 72 is the knee.** Water density drops 8× to 8.13e-5, clearing 1e-4,
  and then *stops moving* — 192 × 96 returns the identical 8.13e-5 for 75 % more
  bytes. R134a density plateaus even earlier, at 7.81e-5 from 96 × 48 onward.
  Past the knee the residual is no longer set by the 2-D grid, so paying for it
  buys nothing.
* T and s do keep improving to 192 × 96, but they are already an order below the
  gate at 144 × 72.

Saturation resolution is a separate, much cheaper axis (`n_sat` costs
`9 × n_sat × 4` bytes — 512 samples is 18 KB), and it is what the exact
two-phase relations and both saturation query forms rest on:

| `n_sat` | Water `(P,x)` | Water `(T,x)` | R134a `(P,x)` | R134a `(T,x)` |
|---|---|---|---|---|
| 64 | 5.87e-4 | 2.28e-4 | 3.04e-4 | 2.40e-4 |
| 128 | 1.33e-5 | 4.54e-5 | 5.94e-6 | 4.48e-5 |
| 256 *(reference)* | 4.02e-6 | 1.12e-5 | 1.41e-6 | 1.11e-5 |
| **512** *(chosen)* | **3.81e-7** | **2.43e-06** | **1.34e-07** | 2.40e-06 |

512 is a 10× accuracy gain on the saturation lines for **18 KB**, or 3.4 % of
the file. Taken.

### `f32` storage, measured rather than asserted

The generator rounds every stored value to `f32` *before* building the
interpolant, so the measurement includes the quantization instead of pretending
it away. Same grid, same samples:

| | Water T / ρ / s | R134a T / ρ / s | bytes |
|---|---|---|---|
| `f64` | 1.084e-5 / 4.512e-5 / 2.077e-4 | 9.311e-6 / 5.894e-5 / 6.984e-6 | 538,144 |
| `f32` | 1.083e-5 / 4.542e-5 / 2.079e-4 | 9.295e-6 / 5.889e-5 / 6.994e-6 | **269,152** |

Every headline number is unchanged to two significant figures. The only
movement anywhere is the two-phase maximum, 1.92e-5 → 3.88e-5 for water —
still 5× below the gate. `f32`'s 6e-8 relative precision is three orders below
the interpolation error it is stored inside, so it is invisible. **Half the
bytes for nothing. Taken.**

### On-disk size

Shipped configuration, `fixtures/proptables/`:

```
header                                        160 B
saturation   9 lines × 512 × 4 B           18,432 B
vapor piece  (144 + 72 + 3×144×72) × 4 B  125,280 B
liquid piece (144 + 72 + 3×144×72) × 4 B  125,280 B
                                          ---------
water.phtab / r134a.phtab                 269,152 B each   (236 KB gzipped)
```

Float payloads barely compress — gzip returns 12 %, so plan on the raw figure.
Two fluids is **526 KB on the wire**, against a 1148 KiB wasm module and a
2048 KiB budget. These are lazily fetched per fluid, not linked into the wasm,
so the wasm budget is untouched; the cost is one ~236 KB fetch the first time a
document names a fluid.

For comparison, option A's `coolprop.wasm` is 3–6 MB for *all* fluids. The
crossover is around 15–20 tabulated fluids. Under that, tables win on bytes as
well as on speed.

## The liquid coordinate had to change

`SaturationSplitTable` measures liquid depth as `h_f(P) − h` capped at **one
depth valid at every served pressure**. That cap is set by the *thinnest*
sliver, which is at low pressure: **68.2 kJ/kg for water, 18.0 kJ/kg for
R134a**. The pump-exit state in `rankine-cycle` is compressed liquid at 8 MPa,
1117 kJ/kg below `h_f(8 MPa)` — **sixteen times outside the rectangle**. The
reference does not care, because it falls through to a native call. **This port
cannot.**

`tools/table-gen` therefore adds a `normalized` liquid coordinate,
`y = (h_f(P) − h)/(h_f(P) − h_cold(P)) ∈ [0, 1]` with
`h_cold(P) = h(P, T_low)`, which follows the whole sliver at every pressure. It
is a strict superset at identical byte cost. Measured at the shipped grid, same
4,000 samples:

| liquid coordinate | Water covered | Water true misses | R134a covered | R134a true misses |
|---|---|---|---|---|
| `absolute` (reference) | 96.8 % | 122 (3.1 %) | 41.9 % | 1908 (47.7 %) |
| `normalized` (shipped) | **99.8 %** | **3 (0.1 %)** | **49.1 %** | **1620 (40.5 %)** |

The `rankine-cycle` pump-exit state goes from a literal `uncovered` to
**4.21e-06**. That single fixture state is the whole argument.

This is the one place the port deliberately diverges from the Java. It is
additive — `absolute` remains selectable with `--liquid absolute`, and the mode
is a header flag — so a faithful `satsplit.rs` port can implement both and the
divergence stays visible rather than baked in.

## What the tables do not cover

Stated now rather than discovered later. **Coverage percentages above are
against a deliberately wide sampling band, not against a document workload.**

* **R134a's superheat ceiling is real.** 40.5 % of R134a samples are declined
  even though CoolProp answers them. Every one of those misses is superheat
  deeper than the served 132.7 kJ/kg, up to 500 kJ/kg — and CoolProp reaches
  them only by extrapolating to **682 K, past its own declared `Tmax` of 455 K
  for R134a**. The band is sized by the reference's `h_top` rule from exactly
  that `Tmax`, which is the correct behaviour: the table declines to interpolate
  where the source data is not valid. All eight R134a document states sit
  comfortably inside. Water, whose `Tmax` is 2000 K, has **3 true misses in
  4000 (0.1 %)**.
* **Subcritical only.** `p_max = 0.75·p_crit`, so nothing supercritical is
  tabulated. `PhPropertyTable`'s doc comment advertises transcritical support;
  `SaturationSplitTable`'s geometry does not use it. A transcritical R744 cycle
  needs a fourth region neither the reference nor this generator builds.
* **No humid air.** `HAPropsSI` is three-input on a different manifold.
  Psychrometrics needs its own decision.
* **No transport properties** (viscosity, conductivity) and **no quality plane**
  — `x` is derived inside the dome and undefined outside.
* **No mixtures or incompressibles.** `ev-thermal-management`'s `EG50`
  (`INCOMP::MEG-50%`) has no dome and this geometry does not apply to it.

## Consequences

* `props/phtable.rs` ports `PhPropertyTable` (bicubic Hermite + the nodal
  finite-difference build), `props/satsplit.rs` ports `SaturationSplitTable`
  plus a `FRPHTAB1` reader. Node values are shipped **already back-filled**, so
  the reader needs no NaN handling and cannot diverge from the oracle by
  tie-breaking the nearest-finite scan differently.
* **The inverse lookups are new code with no Java counterpart.** `(P,T) → h` and
  `(P,s) → h` by monotone bisection on the tabulated surface are what the
  pending fixtures actually call. They are measured here (Water 2.0e-4 worst,
  driven by the same near-zero-entropy corner; R134a 9.4e-6) and they are the
  part of the port with no reference implementation to check against.
* **Parity tolerance is now a live problem, and this decision does not settle
  it.** `tests/parity.rs` compares at `1e-9` relative. The regenerated goldens
  hold full-accuracy CoolProp values. The table path is `1e-7…1e-4`. **No
  table-backed engine can pass a `1e-9` gate on the eight fluid documents.**
  Promoting any of them requires choosing: a per-fixture tolerance for
  property-bearing documents, or shipping `coolprop.wasm` as the accuracy path
  with tables as a Jacobian accelerator only (which is what the Java does).
  Recorded in `docs/status-phase4.md`; owner is whoever promotes those fixtures.

* **Option A is not dead, it is scoped.** `coolprop.wasm` stays the answer for
  supercritical states, humid air, mixtures, transport properties, and any fluid
  without a generated table. The Rust-side LRU in front of it (mirroring the
  20k-entry caches in `props/CoolProp.java`) still applies.
* **This confirms D2.** With tables as the hot path, CoolProp is off the Newton
  inner loop, so the JS-boundary cost that was the only argument for
  `wasm32-unknown-emscripten` no longer applies.
* **Revisit if** the unmeasured speed half of the spike shows table lookup is
  not the bottleneck anyway, or if a supercritical/psychrometric document
  becomes a target — the first needs a fourth region, the second a different
  decision entirely.
