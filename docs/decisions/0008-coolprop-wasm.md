# D8 — `coolprop.wasm` becomes the accuracy path

**Status:** Decided · **Date:** 2026-08-07 · **Implementation:** in progress (outside this repo)

## Decision

Build CoolProp for WebAssembly and use it as this build's real-fluid property
source. Work on it is under way separately; **this repo picks it up once that
implementation lands**. No humid-air backend, no `air.phtab`, and no further
`FRAUX1` grids are to be written in the meantime — they would be superseded.

This is the second of the two exits
[D1](0001-property-backend.md) named when it chose precomputed `(P,h)` tables:
*"a per-fixture tolerance, or shipping coolprop.wasm as the accuracy path."*
The first has been taken 23 times in `fixtures/tolerances.json`. This is the
other one.

## Context — what forced the question

The trigger was the humid-air gap: 7 of the 26 pending parity fixtures fail
because no shipped backend implements `HAPropsSI`, and the obvious remedy
looked small. It is not, and the measurement is the reason this decision is
being taken now rather than later.

Measured against the vendored `libCoolProp` (CoolProp 8.0.0), over the
near-ambient HVAC band those fixtures actually use — see
`fixtures/humidair/reference.json`, 912 points, generated by
`tools/humidair-ref/gen.py`:

| Path | Ideal-gas ASHRAE error |
|---|---:|
| `(T,W) → H` | **2.4e-04** |
| `(T,R) → H` | **2.7e-03** |

The `(T,R)` path is an order worse because relative humidity converts through
the **enhancement factor**: `W = 0.621945 · f·p_ws / (P − f·p_ws)`, and `f`
reaches **1.0041** across this band. An ideal-gas model omits it entirely.

The correction is not simply "transcribe ASHRAE RP-1485", which was the
initial plan. **CoolProp's `HAPropsSI` *is* RP-1485 — evaluated against
IAPWS-95 (water) and Lemmon (air).** The consequence is measurable: the
IAPWS-95 *ancillary* saturation equation, the cheap one, is already **7.1e-5**
off CoolProp's own saturation solve at these temperatures, and `W` depends on
`p_ws` roughly linearly. That is a floor on the `(T,R)` path before any
enthalpy error is added — so a tolerance entry would have to be ~1e-3, which
is 100× looser than the loosest entry in the file and would assert almost
nothing about a psychrometric document.

Reaching the ~1e-6 a defensible entry needs therefore means porting two
reference equations of state, not a virial layer. At that point the question
is no longer "how do we serve humid air" but "which property architecture is
this build committing to", and `coolprop.wasm` answers it directly by
supplying exactly those equations of state.

## What it clears

Twelve of the 26 pending fixtures, versus seven for a humid-air backend alone:

| Gap | Fixtures |
|---|---:|
| `HAPropsSI` humid air | 7 |
| No `(P,h)` **state** table for `Air` (D7 gave `(P,T)` transport only) | 3 |
| `Viscosity`/`Conductivity` at `(P,T)` off the dome (`hx-correlations-fluid`) | 1 |
| `CompressibilityFactor` (`thermo-compliance`) | 1 |

It should also retire most of `fixtures/tolerances.json`. Those 23 entries
exist because the tables are 1e-7..1e-4 from CoolProp; served by CoolProp
itself the documents would grade at the default 1e-9. **Note the trap:** that
file's own rule is that *"an entry whose fixture passes at the default 1e-9
makes the parity test FAIL"*, so adopting `coolprop.wasm` requires deleting
the dead entries in the same change, not afterwards.

## Consequences and open risks

* **Bundle budget is the gating constraint, and it is already tight.** The
  wasm is 3042.3 KiB against the 3072 KiB budget — **29.7 KiB of headroom**.
  CoolProp's fluid data is not small. Either the budget moves, or the `.phtab`
  / `.fraux` artefacts it replaces come out (~678 KiB of data section today),
  or the property backend lazy-loads as a separate chunk. This has to be
  settled as part of the integration, not discovered by it.
* **The `RealFluid` seam already exists and should be reused.**
  `props/propfun.rs` defines the trait — `props_si`, `props1_si`,
  `ha_props_si`, `served_fluids`, `describe` — mirroring the four C functions
  `props/CoolProp.java` binds. A `coolprop.wasm` backend is a new
  implementation of that trait, not a new architecture. `ha_props_si`'s
  declining default is the hook the humid-air fixtures need.
* **The tables should not be deleted reflexively.** They are the offline and
  size-constrained path, and D1's reasoning for them still holds if the
  CoolProp bundle proves too large. Prefer selecting a backend over removing
  one until the size question is answered with a measurement.
* **`fixtures/humidair/reference.json` stays useful.** It grades a humid-air
  implementation against CoolProp 8.0.0 in CI, where no `libCoolProp` exists —
  including the `coolprop.wasm` one, which should reproduce it to round-off.

## What was explicitly not done

No humid-air code was written. The ideal-gas model was measured and rejected
on accuracy, the RP-1485 route was scoped and found to require the two
reference equations of state, and the work stopped there rather than
committing an implementation that would be superseded. What exists is the
ground truth and this record.
